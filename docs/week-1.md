# Неделя 1: модель и симулятор

Код этой недели пишешь сам, включая тесты. Ниже требования и проверки, по которым видно, что готово.

## 1. Доменная модель: `internal/domain`

Дерево: вид спорта → турнир → матч → рынок → исход.

| Сущность | Что хранит |
|---|---|
| `Sport` | ID, название: футбол, CS2, Dota 2 |
| `Tournament` | ID, вид спорта, название |
| `Match` | ID, турнир, команды, время начала, статус (до матча, идёт, завершён), счёт, **версия** |
| `Market` | ID, тип (исход матча, тотал, фора), параметр (например 2.5 для тотала), статус (открыт, приостановлен, закрыт) |
| `Outcome` | ID, название (П1, X, П2, больше, меньше), коэффициент |

Изменения, которые приходят от провайдера:

| Изменение | Что делает |
|---|---|
| `MatchCreated` | новый матч со всеми рынками |
| `OddsChanged` | новый коэффициент исхода |
| `MarketSuspended`, `MarketResumed` | приостановка и открытие рынка |
| `ScoreChanged` | счёт поменялся |
| `MatchFinished` | матч завершён, рынки закрыты |

У каждого изменения есть ID матча и **версия матча**. Правило применения:
- версия = текущая + 1: применить, версия матча растёт;
- версия ≤ текущей: дубль или опоздание, пропустить;
- версия > текущая + 1: пропуск в последовательности, вернуть ошибку. Что с ней делать, решим на неделе 2.

Проверки (табличные тесты):
- [ ] применение по порядку меняет состояние и версию;
- [ ] дубль и опоздавшее изменение не меняют ничего;
- [ ] пропуск версии возвращает ошибку, по которой `errors.Is` находит `ErrVersionGap`;
- [ ] коэффициент приостановленного рынка можно поменять, но статус остаётся «приостановлен»;
- [ ] после `MatchFinished` любые изменения матча, кроме дублей, возвращают ошибку;
- [ ] коэффициент не больше 1 — ошибка (вспомни упражнение 01).

## 2. Формат сообщения

JSON на первое время, на неделе 4 можно сравнить с protobuf по размеру и скорости.

```json
{"type":"odds_changed","match_id":"m-42","version":17,"ts":"2026-11-20T18:31:05.123Z",
 "market_id":"m-42-total-2.5","outcome_id":"over","odds":1.92}
```

`ts` — время на стороне провайдера. По нему потом меряем задержку до клиента.

Проверки:
- [ ] каждое изменение кодируется в JSON и обратно без потерь;
- [ ] неизвестный `type` при декодировании даёт ошибку, а не панику.

## 3. Симулятор: `cmd/simulator`

Что делает:
- создаёт N матчей по разным видам спорта с рынками «исход матча» и «тотал»;
- в цикле с заданной частотой меняет коэффициенты случайных исходов;
- иногда случается гол: рынок приостанавливается, через 1–3 секунды открывается с новыми коэффициентами, счёт меняется;
- матч завершается через заданное время.

Флаги: число матчей, изменений в секунду, `seed`, адрес RabbitMQ. Одинаковый `seed` даёт одинаковую последовательность.

Отправка: обменник `kefline.feed` типа topic, ключ `feed.<sport>.<match_id>`. Сообщения persistent.

Проверки:
- [ ] генератор без RabbitMQ (отдельная функция) с одним `seed` выдаёт одну и ту же последовательность, версии каждого матча идут подряд с 1;
- [ ] за 10 секунд при 1000 изменений в секунду выдано 9–11 тысяч изменений;
- [ ] после `docker compose up` симулятор публикует сообщения, в веб-консоли RabbitMQ видна скорость.

## Порядок

1. `internal/domain`: типы и применение изменений с тестами. Без RabbitMQ.
2. Кодирование в JSON с тестами.
3. Генератор изменений с `seed` с тестами.
4. Отправка в RabbitMQ и флаги в `cmd/simulator`. Для этого шага нужен Docker.

Библиотека для RabbitMQ: `github.com/rabbitmq/amqp091-go`. Для флагов хватит стандартного `flag`.

## Решения записывай

Каждое неочевидное решение — короткий файл в `docs/decisions/`: что выбрал, из чего, почему. Например, почему JSON, а не protobuf на старте, или почему версия на матч, а не на исход. На собеседовании это половина разговора.
